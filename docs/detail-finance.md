# 로컬 게임의 자산·거래 기록 상세

이 문서는 공개판 이후 main에 이어 적용한 로컬 회계 정합성 개선을 설명한다. 가격 생성, 호가 단위, 체결 가격, 레벨 제한, 수수료·차입 이자·강제청산 기준을 새 금융 모델로 바꾸지 않는다. 금액은 모두 게임 안의 원(KRW) 단위이며 실제 거래 서비스의 규칙을 뜻하지 않는다.

## 자산의 분리

공매도 진입 시 현금에서 예치증거금을 빼므로 증거금은 현금과 별개의 자산으로 남는다. 기존에는 총자산식에서 이 자산이 빠져 진입 즉시 손실이 발생한 것처럼 표시됐다.

`calculateAssets`와 `useGameCalculations`는 다음 값을 공유한다.

| 필드 | 의미 |
| --- | --- |
| `safeCash` | 현재 사용 가능한 현금. 공매도에 예치한 금액은 제외 |
| `stockValue` | 보유한 매수 포지션의 현재 평가금액 |
| `shortValue` | 공매도 미실현 손익의 합. 기존 필드 의미를 유지 |
| `shortMargin` | 공매도 포지션에 예치된 증거금의 합 |
| `shortEquity` | `shortMargin + shortValue` |
| `grossAssets` | `safeCash + stockValue + shortEquity` |
| `leverageDebt` | 매수 포지션에 연결된 레버리지 차입 원금 |
| `totalAssets` | `grossAssets - creditUsed - creditInterest - leverageDebt` |

공매도 손익은 `(진입 평균가 − 현재가) × 잔여 수량`이다. 따라서 가격과 이자가 그대로면 공매도 진입·부분 청산·전체 청산 자체로 순자산이 바뀌지 않는다. 증거금보다 손실이 커진 포지션의 `shortEquity`는 음수가 될 수 있으며 손실을 0으로 자르지 않는다.

`getShortPositionMargin`은 저장된 유효한 `margin`을 우선 사용한다. 구형 포지션에 이 필드가 없으면 기존 예치 비율인 `entryPrice × quantity × SHORT_SELLING.marginRate`를 사용한다. 유효한 0원 증거금은 0원으로 유지한다. 시세를 찾을 수 없는 포지션도 예치금까지 사라지지는 않는다. 해당 포지션의 현재 손익은 기존과 같이 시세 없이는 산출하지 않는다.

화면의 자산 계산, 10초 간격 자산 기록, 신용 마진콜의 총자산 분자는 같은 함수를 사용한다. 기존 신용 비율 `grossAssets / creditUsed`와 경고·청산 임계값은 유지한다. 자산 기록은 과거 기록값이며 최신 총자산과 구분한다.

## 수동 거래와 예약 주문

- 매수·매도 수수료는 기존 할인 규칙과 정수 내림을 유지한다. 매수 원가는 매수 수수료를 포함한다.
- 매수 포지션 일부 매도 시 평균 원가와 연결 차입 원금을 수량 비율로 배분한다. 현금에는 매도대금에서 수수료와 상환할 차입 원금을 뺀 금액이 반영된다.
- 예약 매수는 기존 포지션의 차입금·증거금·레버리지·최초 매수 시각을 보존한다. 추가 현금 매수분 때문에 기존 차입금이 지워지지 않는다.
- 예약 분할 매도도 동일하게 차입금을 비례 상환하며 나머지 포지션의 원가와 부채를 남긴다. 기존 지정가·손절·시장가 체결 가격 규칙은 그대로다.
- 공매도 진입은 기존 150% 증거금을 예치한다. 수동 청산 현금은 `반환 증거금 + 실현 손익`이며 별도의 거래 수수료를 새로 만들지 않는다. 틱별 공매도 차입 이자는 기존 경로에서 차감한다.

수동 공매도 청산은 `type: 'cover'`인 로컬 거래내역에 기록한다. `quantity`, `price`, `profit`, `timestamp`와 함께 `marginReturned`를 남기며 `total`은 실제 현금 증감인 반환 증거금과 손익의 합이다. 총 거래 수와 일일 거래 수, 총·일일 실현손익, 연승이 함께 갱신된다. 서버용 `recordTrade('COVER', stockId, quantity, { orderType: 'market' })` 호출 형식은 바꾸지 않는다.

`totalProfit`은 기록된 청산 거래의 실현손익 누계다. 현재 총자산 변화 전체를 의미하지 않으며 미실현 손익, 배당, 보상, 별도 차입 이자는 구분해야 한다.

## 거래 내역과 통계 표시

거래 내역은 매수·매도·공매도·공매도 청산을 구분한다. 공매도 진입 금액은 예치 증거금, 청산 금액은 반환 증거금과 손익을 합친 현금 증감으로 표시한다. 강제청산 이유, 매도 시 차입금 상환액, 실제로 기록된 실현손익도 별도로 보여준다. 기록에 없는 수익률을 `%`로 합성하지 않으며 소액 상품의 가격과 손익은 소수점 정밀도를 유지한다.

통계의 청산 거래에는 매도와 공매도 청산을 모두 포함한다. 승률의 분모는 손익이 기록된 청산 횟수이며 본전 거래도 포함한다. 본전이나 손익 미기록 거래는 연승·연패를 끊고 손실로 세지 않는다. 이익도 손실도 없으면 총이익/총손실 비율은 계산 불가로 표시한다.

자산 기록에서 인접한 두 관측값의 단순수익률을 계산하되 직전 자산이 0 이하이거나 숫자가 유효하지 않은 구간은 제외한다. 빠진 구간을 건너뛰어 새 구간을 합성하지 않는다. 평균과 모집단 표준편차를 각각 표시하고 유효 표본 수를 알린다. 변동성은 두 구간 이상일 때만 계산한다. 이 값들은 샤프 비율이나 연율 위험 수치가 아니다. 최대낙폭도 현재 보존된 기록 안의 최고점에 대한 값이며 저장되지 않은 과거 최고점·생애 전체 낙폭을 추정하지 않는다. 기록되지 않은 보유시간을 60초로 가정하던 계산은 제거했다.

시즌 결과도 같은 청산 범위와 본전 처리 기준을 사용하고 현재 순자산, 실현손익 누계, 기록 구간 낙폭을 구분한다. Firebase 설정이 없으면 온라인 제출을 비활성화하고 연결되지 않았음을 알린다. 설정이 있는 경우 기존 제출 payload를 그대로 전달하며, 로컬 평가액과 서버 재현 결과가 같은 값이라고 약속하지 않는다.

## 강제 청산

신용 강제청산의 기존 5% 매각 차감은 유지한다. 매수 포지션에 연결된 차입금은 매각 후 현금에서 상환하므로 포지션 삭제와 함께 부채가 사라지는 오류를 방지한다. 이후 기존 순서대로 신용 이자와 신용 원금을 상환한다. 시세가 없는 포지션은 임의의 가격으로 청산하거나 삭제하지 않는다.

공매도 강제청산도 실제 잔여 증거금을 반환하고 손익을 정산한다. 같은 틱에 발생한 기존 차입 이자를 별도로 차감한다. 다른 포지션이 청산될 때 시세가 없는 공매도 포지션이 함께 삭제되지 않는다.

두 강제청산은 기존 현금 흐름과 일치하는 로컬 거래내역·실현손익·거래 수를 한 번 기록한다. 내역의 `reason`은 `credit-liquidation` 또는 `short-liquidation`이다. 수동 행위인 것처럼 새 서버용 `SELL`/`COVER` 로그를 만들지 않는다. 기록 식별자 생성과 차트 관측은 추가 시장 난수를 소비하지 않는다.

## 시장 관측 연결

`useGameLoop`의 선택적 `onObservation({ stocks, timeMs, gameDay, gameTime })` 콜백은 완료된 실제 게임 루프마다 한 번 호출된다. 가격이 그대로인 틱도 포함한다. 콜백 교체는 타이머를 재생성하지 않으며 관측 오류가 이미 계산된 계좌 갱신을 막지 않는다. 이 연결은 기존 30개 가격 배열과 별개이며 게임을 다시 실행하거나 가격 생성기를 호출하지 않는다. 수신 측은 관측값을 읽기만 하고 전달받은 게임 객체를 수정하지 않아야 한다.

게임 루프는 저장 복원이 끝나기 전에는 실행하지 않는다. 복원된 `currentDay`를 마지막으로 처리한 거래일로 받아 같은 날 다시 열었을 때 일일 통계·시가를 초기화하거나 신용 이자를 중복 부과하지 않는다. 오프라인 동안 여러 날이 지났을 때에는 기존처럼 새 거래일 전환과 이자를 한 번 처리하며 누락 일수만큼 소급하지 않는다. 새 게임의 `gameStartTime`으로 바뀌면 거래일·연도 감시값도 초기화하여 이후 2일째와 첫 연도 말 알림이 정상 작동한다. 연도 종료 알림의 이미 표시 여부는 별도 저장하지 않으므로 연도 말 저장을 다시 열면 해당 창이 다시 나타날 수 있다.

## 저장·온라인 검증의 경계

이 변경은 저장 버전 4와 기존 시즌 전환 정책을 변경하지 않는다. 새 필드는 파생값 또는 거래내역의 부가 설명이며 서버 제출 형식을 확장하지 않는다.

**로컬 순자산 수정은 온라인 순위의 재현·검증 완료를 의미하지 않는다.** 현재 서버 `functions/src/replay/engine.ts`에는 로컬과 다른 별도 거래 모델이 남아 있다. 서버는 공매도 매도대금을 현금에 더하는데, 평가 시 다시 진입대금에서 현재 부채를 뺀 손익을 더한다. 이로 인해 미청산 공매도 진입대금이 중복 반영될 수 있다. 서버의 commission·매도 tax와 로컬의 수수료 내림·할인·증거금 방식도 다르다. 이 개선에서는 미배포 Firebase 서비스의 재현 엔진·수수료 정책·프로토콜을 수정하거나 검증됐다고 간주하지 않는다.

## 검증

`detail-finance.test.js`는 상승·동일·하락·증거금 초과 손실에서의 공매도 분할 청산, 가중 평균 진입, 레버리지 원가·부채 상환, 예약 주문, 신용·공매도 강제청산과 불변 입력을 독립적인 금액으로 대조한다. `useGameLoop.observation.test.js`는 동일가 틱의 관측 횟수, 최신 콜백, 난수 비소비, 자산 기록의 증거금 포함, 강제청산 로컬 기록의 단일 반영과 서버 로그 미추가를 확인한다.

`FinancialReports.test.jsx`는 공매도·청산·강제청산 표시, 미세 가격 정밀도, 본전과 누락 손익, 0·음수 자산 경계, 기록 구간 수익률과 낙폭의 실제 화면 의미를 검증한다.

`SeasonEnd.finance.test.jsx`는 동일한 청산 통계, 미연결 제출 비활성, 연결 시 원래 제출 payload와 API 재렌더의 중복 요청 방지를 확인한다. 루프 테스트에는 복원 전 실행 차단, 같은 날 복원, 오프라인 다일 경과의 한 번 처리, 새 게임의 2일째 처리, 첫 연도 말 알림과 재초기화를 포함한다.
